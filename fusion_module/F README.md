# C模块：多模态融合与交互业务技术文档

## 1. 模块概述
本模块是整个设备听诊系统的“大脑”，负责接收 A 模块（音频故障诊断）和 B 模块（视觉表计识别）的推理结果，通过规则引擎进行多模态数据对齐与融合，并调用板载轻量化大语言模型（LLM），生成人类可读的巡检结论和自动化工单。

## 2. 核心技术实现

### 2.1 多模态数据对齐与通信协议
- **通信方式**：采用 TCP Socket 通信，C 模块作为 Server 端监听 `9000` 端口，A、B 模块作为 Client 端。
- **数据格式**：严格定义 JSON Schema 进行数据交互，避免多模态数据冲突。
  - A模块格式：`{"audio": {"fault_class": "xxx", "confidence": 0.xx}}`
  - B模块格式：`{"vision": {"device_type": "xxx", "status": "xxx", "confidence": 0.xx}}`
- **缓存对齐机制**：引入全局数据缓存池（`data_cache`），当 A 或 B 单独发送数据时，C 模块暂存数据并阻塞等待；当两路数据均齐备后，立刻触发融合逻辑。

### 2.2 规则级融合策略 (Rule-based Fusion)
不盲目依赖大模型做判定，而是采用确定性规则引擎保证工业可靠性：
- 若音频正常且视觉正常，判定为“正常”。
- 若音频判定为“轴承磨损”（置信度>0.8）或“机械松动”，判定为“报警”。
- 若视觉检测到仪表状态为“alarm”或“unreadable”，结合设备型号进行预警。
- 规则引擎输出结论、报警等级（正常/预警/报警）及结构化证据。

### 2.3 端侧大语言模型集成 (LLM Integration)
- **推理后端**：基于 RISC-V 板载的 `llama-server`（监听 8080 端口），采用兼容 OpenAI 的 `/v1/chat/completions` 接口。
- **提示词工程（Prompt Engineering）**：严格限制模型输出范围，要求模型根据“综合判定”和“证据”生成工单，禁止编造未提及的故障，降低大模型“幻觉”问题。
- **语义渲染**：将生硬的结构化数据转化为符合工业巡检规范的自然语言工单（含处置建议）。

## 3. 性能优化与高可用设计
- **超时降级机制（Fallback）**：大模型推理受板端算力限制，若 LLM 推理超时（设置阈值为 15 秒）或服务崩溃，系统会自动触发降级策略，直接输出基于规则引擎的结构化文本。**确保极端情况下系统依然能输出工单，不发生阻塞死机。**
- **算力节约策略**：若规则引擎判定当前设备状态为“正常”，则直接跳过 LLM 推理过程，直接返回预设的正常话术，大幅节省端侧算力。
